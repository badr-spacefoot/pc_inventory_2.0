# Backend remediation — 15 September 2026

These are local source and migration changes. No production SQL, secrets, DNS, Edge Function deployment or Storage deletion was performed by this work. The original audit remains a dated record of the pre-fix snapshot.

## Changes by finding

| Finding | Local correction |
|---|---|
| B01 sessions | Replaced role-bearing stateless tokens with signed session IDs backed by `admin_sessions`. Every request loads the active account and current role. Password, role and activation changes revoke sessions transactionally; user deletion cascades them. Session minting locks and rechecks the verified password hash to close the password-reset race. POST `/auth/logout` revokes the current session. Old stateless tokens and legacy shared admin login are rejected. |
| B02 stored XSS | Frontend owner escaped the scan-history HTML sink. Backend still treats collector OS fields as untrusted data; safe rendering is the actual fix. |
| B03 login attempts | Added persistent atomic attempt windows: 8 attempts per normalized account per 15 minutes, plus 300 aggregate attempts per minute. No client-supplied forwarded IP is trusted as an identity. Throttle failures deny login; disabled accounts receive generic credential failures. |
| B04 outbound fetch | Benchmark, legacy CPU reference and official CPU-release HTTP reads use a shared HTTPS host allowlist, reject credentials/nonstandard ports, reject redirects before following, apply an 8-second deadline and enforce streamed byte limits. Request-provided benchmark sources are limited to PassMark/GitHub raw hosts; arbitrary private/localhost URLs are rejected. |
| B05 collection identity | Collectors no longer edit existing user profiles by email. Unknown collectors cannot overwrite a known device by claiming its serial. A script credential becomes bound to its first newly registered device. An ADMIN can create a recipient-bound collection invite with `deviceId` to authorize an existing machine; the frontend owner added the selection field. Invite email binding is enforced server-side when a profile is issued. New-device insertion cannot overwrite a concurrent insert on dedupe conflict. |
| B06 invite race | Collection invite consumption moved into a single conditional SQL UPDATE with RETURNING. Account invite acceptance also now locks, validates, creates the account and marks acceptance in one transaction; the RPC response excludes the password hash. |
| B07 fleet completeness | Fleet retrieval pages by stable device ID until an empty page, rather than assuming a requested page size equals the gateway cap. A regression uses 1,101 rows and a simulated 97-row gateway cap. |
| B08 job progression | Jobs persist their device membership. Workers claim distinct items with leases and UUID fencing tokens; result completion recomputes counters from finished items. Cached skips cannot repeatedly count the same device, stale claims cannot complete new leases, and completed/canceled jobs are not reopened by late results. Provider counts/statuses remain aggregated. |
| B09 invoice provenance | Purchase-invoice deletion invalidates book value and invoice confidence transactionally, retaining independent market-price fields. The handler recalculates against the remaining invoice or falls back to existing market/rule estimates without new external market requests. A failed recalculation leaves an explicit pending/low-confidence state rather than stale invoice-backed confidence. |
| B10 Storage and retries | Uploads create a durable cleanup obligation before writing their object. Invoice deletion—including device cascade—queues object cleanup transactionally. The cleanup endpoint retries removals and checks current invoice references. Queue versions prevent a stale worker from deleting a concurrent requeue. Invoice requests support a per-device unique `requestId`/`idempotencyKey`; frontend owner retains the UUID for retry. Invoice-added device history is recorded in the same transaction as insertion, including when subsequent valuation work fails; retry cannot duplicate that event. |
| B11 request/file limits | All body-reading handlers are POST routes and share bounded ingestion (16 KiB login, 1 MiB ordinary JSON, 14 MiB invoice JSON). Base64 length is checked before decoding and decoded data is capped at 10 MiB. PDF/image magic bytes are checked against declared MIME. GET/DELETE handlers do not parse request bodies; there are no PUT/PATCH handlers. Credential/data responses include no-store and nosniff. |
| B12 audit failures | Audit/notification/token-insert errors are checked instead of ignored. Metadata-only transactional audit triggers protect device, invoice and admin-account mutations even if the subsequent application audit call fails. |
| B13 grants | Migration revokes unnecessary anon/auth/public privileges, including TRUNCATE, on enrichment jobs and new security tables; RPCs are executable only by service_role. RLS is enabled on every new table. |

## Files and deployment contract

- Migration generated using Supabase CLI: `supabase/migrations/20260915132127_audit_security_data_integrity.sql`.
- Consolidated `supabase/schema.sql` includes the same migration under the `AUDIT_SECURITY_DATA_INTEGRITY` marker. The original baseline plus the migration executes in the embedded PostgreSQL test fixture.
- API entry point changes remain in `supabase/functions/inventory-api/index.ts`, with bounded I/O/session/MIME helpers in `core/security.ts` and the existing response/type helpers updated.
- Deploy the migration before the new Edge Function; keep the new frontend/logout/enrollment UI release coordinated. All existing administrator sessions will require login again when the new API is activated. Named admin accounts must already exist; the first-account bootstrap still works with the bootstrap password. Shared legacy password-only administration is intentionally disabled.
- Existing collector credentials without device enrollment cannot update a known machine after rollout. Generate an invitation selecting that machine and its recipient to authorize it. Newly issued generic invitations remain valid for registering new machines.
- An in-progress enrichment job from before this migration receives a fresh persisted membership snapshot on first processing; old aggregate counters are not trusted as proof of distinct completed devices.
- Maintenance endpoint: POST `/admin/maintenance/storage-cleanup`, authenticated with ADMIN or `x-enrichment-sync-token`. Parent integrated a daily call into the existing scheduled workflow. It handles up to 50 queued objects per call. Failed Storage removals remain queued; linked successful uploads are removed from the queue after their safety delay. Verify scheduling and errors in the deployed environment.
- Self-hosted signed invoice downloads: set server-only `SUPABASE_PUBLIC_URL=https://parc-api.piqa.fr` while keeping `SUPABASE_URL=http://api-gw:8000` for internal API access. The public setting must be a bare HTTPS origin without credentials/path/query/fragment. Only the returned signed URL origin changes; the Storage object path and signed query remain intact. Unexpected source origins/paths are rejected. Leave the setting empty on managed Supabase to preserve its normal signed URLs. Parent owns the environment template/overlay documentation.

- Deno formatting and targeted ESLint passed for the backend source/tests.
- 15 actual PostgreSQL regression tests pass using PGlite: migration execution, session invalidation/logout, stale password mint rejection, durable throttling, invite use/revocation, atomic account acceptance/conflict rollback, job membership/cached skips/fencing/counters, invoice invalidation/cascade cleanup, stale cleanup acknowledgement, invoice request deduplication, grants and transactional audit rollback.
- 7 boundary/helper regressions pass: URL rejection, redirect prevention, stream cancellation/size bounds, file signatures, revoked/expired/disabled session validation, fleet pagination above a lower gateway cap, and public signed-URL origin mapping without changing signatures. Together with the 15 database regressions, the latest focused run is 22 passed.
- The existing backend suite also passed before the last added regressions (117 passed, 3 explicitly gated live-network tests skipped). Parent runs the final whole-project gate after integration; this record does not substitute for that result.
- PGlite is a real embedded PostgreSQL engine; it does not emulate the Supabase gateway, Storage HTTP service or simultaneous independent database connections. Tests simulate stale/reclaimed worker interleavings but do not certify a multi-worker deployment under load.

## Remaining environment validation

1. Deploy migration/API/UI to isolated staging and exercise real role/auth routes, logout, password resets, personalized device re-enrollment, revoked invites, invoice retries and Storage cleanup. Recheck live grants after migration.
2. Test concurrent HTTP workers against PostgreSQL, failed external requests, object removal retries, and at least one backup/restore covering both DB and Storage.
3. The HTTPS host allowlist substantially reduces SSRF exposure but does not implement DNS/IP pinning. A VPS should block outbound access to private/metadata networks at the network/proxy layer; verify DNS and egress behavior before self-hosting. Redirecting provider URLs now fail safely; configure vetted direct canonical source URLs and verify their availability. We did not contact provider URLs as part of these fixes.
4. Login MFA/SSO, perimeter volumetric protection, malware scanning of structurally valid documents, and organization-wide data retention policies are external/product controls, not established by these local changes. Magic-byte checks do not certify a document as malware-free.
5. Multi-step collection/history/notification operations can still encounter a service failure after a primary write. Errors are now visible, critical mutations have transactional metadata audit, and invoice/job operations are retry-aware; a complete remote-provider transaction is not possible. Verify recovery UX with injected staging failures.

No claim is made that production is corrected until the migration, function and frontend are deployed and the environment checks pass.
